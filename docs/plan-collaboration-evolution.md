## Outcomes

1. A user-selected model change does not require returning to the original model merely to continue a task.
2. A session can proactively hand work to a fresh session before context exhaustion. The old session is archived only after the replacement has demonstrably taken over.
3. Independent tasks can run concurrently with separate planner, writer, reviewer, integrator and verifier assignments when those roles help. Small tasks keep a short path.
4. Installed users can access the remaining supported native/history operations, with actual host/version support distinguished from fixtures, library exports and unknown capabilities.

## Model policy

Treat model/provider/reasoning as mutable runtime observations, distinct from logical task identity, native session, authority epochs and required capabilities. Default continuation permits a user-selected model change; a task may explicitly constrain a model for reproducibility or capability needs. Preserve the requested choice. A changed model must not make old observations look new, and prior successful tool use must not automatically prove the new runtime still exposes that tool. Revalidate only what materially changed, reuse unchanged fresh evidence, and explain any concrete missing capability or explicit constraint.

Do not expose another generic profile-migration layer unless the reproduction proves one is required. Keep backward compatibility and distinguish configuration labels from actual observed settings. Regression coverage must reproduce the original block, successful changed-model continuation, actual capability loss, stale evidence and an explicitly locked policy.

## Rollover protocol

Proposed sequence (map to existing protocol states before implementing):

1. A supported usage event or completed-work milestone creates one rollover intent keyed to task/session/generation. A planning default is a configurable 70% preparation watermark and 85% transfer request watermark; validate these against actual host accounting before shipping. Reserve enough headroom for the bundle and confirmation; never wait deliberately for a full context error.
2. At a safe boundary, preserve objective, decisions, scoped files and hashes, current diff/base, pending tools/messages/approvals, accepted/rejected findings, claims/epochs, validation evidence, next concrete action and recovery instructions. Context is private and bounded; checkpoints do not invent a semantic summary.
3. Quiesce the old writer for the affected resources using demonstrable protocol/native evidence. It may remain alive for recovery, but cannot keep writing those resources after transfer. A pane's idle state is insufficient. Start the replacement in a visible pane with daily settings and the current selected model; initially it receives context/read access only.
4. Verify exact replacement identity/cwd/capabilities, bundle digests and correlated ACK. Complete the existing guarded writer or coordinator handoff as appropriate; update bindings/epochs once. Coordinator dispatch freeze must not stop unrelated independent work unnecessarily.
5. The replacement performs and reports its first bounded authorized work. Only then mark the old session archived with a durable successor link. Archive means reversible retained history and removed active routing, not transcript deletion, unknown-process termination or closing a user's pane. Native archive availability is host-specific; unsupported native archive must be reported separately from task metadata archive.
6. Failed bootstrap/ACK leaves ownership unchanged. Failure after transfer requires explicit recovery using current epochs and observed state, not silent rollback or duplicate writers. Duplicate triggers reuse the existing intent and replacement.

Initial automation is opt-in by workspace/task policy and authorized here for fixture/owned collaboration sessions. Do not alter the user's unrelated sessions, global settings or model choices. Compaction and rollover are separate decisions; already-running host compaction must not create competing successors. If a host lacks a reliable usage event, use a documented explicit milestone/command path until a real adapter exists.

| Reviewer | Independent spec/correctness/compatibility review | Review artifact only |
| Integrator | Reconcile accepted artifacts and shared interfaces | Explicit integration scope |
| Verifier | Targeted/full/package/live validation | Isolated test output; fixtures only unless authorized |

Select roles per task complexity and capabilities, not fixed harness stereotypes or a mandatory six-agent pipeline. Start with the existing Pi writer plus one visible Pi investigator; grow only for independent work. The same harness can fill different roles in different assignments. The same writer cannot be its own sole acceptance authority. For small tasks combine planner/integrator or reviewer/verifier; for substantial tasks let independent investigation, implementation and review overlap on immutable artifacts.

Use dependency edges and explicit input revisions rather than a new authoritative scheduler. Shared-interface changes happen before consumers or at an integration barrier. Writers need disjoint claims; broad existing claims must be explicitly narrowed/released before another writer overlaps. Read-only audit can run in the shared checkout. Worktrees are an option for conflicting modules after preserving the current dirty baseline; never reset/stash/discard the user's work to create one. Parallel per-scope manifests must distinguish another participant's expected edits from unexplained drift. One owner controls shared build/test outputs that clean `.build` or `dist`; parallel workers use isolated outputs otherwise. Limit concurrency to useful work and track critical-path time/coordination cost.
