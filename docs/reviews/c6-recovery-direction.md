# C6 explicit task recovery: implementation direction

Expose the preserved uncertainty/reconciliation and task-lock recovery primitives. Reuse existing lifecycle/store behavior and task namespace checks. This slice never queries, stops, restarts, adopts or retries a native execution and never silently releases claims.

## Public CLI

- `pappra collab recovery inspect --task-root <abs> [--json]`
- `pappra collab recovery reconcile --task-root <abs> --request <abs request.json> [--apply] [--json]`
- `pappra collab recovery lock-break --task-root <abs> --request <abs request.json> [--apply] [--json]`

Use versioned `pappra/collaboration-recovery/1` results and a strict discriminated `pappra/collaboration-recovery-request/1` request schema. Reject wrong-action/unknown/duplicate flags and fields. Bound request JSON at 1 MiB with the shared special-file-safe loader. No public clock override or unbounded raw evidence output.

Inspect is read-only: bounded open/resolved uncertainty summaries with full counts/truncation, task/revision/current coordinator epoch, task-lock/transaction observations and a fingerprint of the current lock content. It returns needs-input/exit 1 when uncertainty or interrupted lock state needs recovery; a clean state exits 0, invalid request/layout exits 2 or the established typed state-failure path. Reported PID liveness is observation, not proof of execution ownership or stop.

## Reconcile

Request: explicit action, actor, current owner_epoch, uncertainty_id, nonempty resolution, resolution_evidence reference, optional expect_revision and optional explicitly requested set_state. Preserve exact input meaning; no default state transition.

- Reuse resolveUncertainty and, only for explicit set_state, transitionAttempt against the entry's exact subtask/attempt. Use one guarded transaction with current epoch and optional revision checks.
- Resolution is the caller's recorded conclusion, not a fresh native query or proof generated by Pappra. Evidence references must be explicit; do not invent approval, cancellation, completion, stopped-writer or live-ownership evidence.
- An invalid/denied state transition refuses the entire transaction: resolving uncertainty must not commit first or hide a failed transition inside an outer successful response. Missing attempt context with set_state refuses instead of ignoring the requested state.
- Preserve all existing transition authorization/evidence checks, approval boundaries, claims under cancel uncertainty and stale-result behavior. Do not auto-clear cancel_pending or release claims when resolution is recorded. If existing native transition evidence cannot be represented safely, BLOCK that concrete case rather than accepting arbitrary unauthenticated proof as verified.

## Task lock recovery

Request: explicit actor, current owner_epoch, nonempty reason, `confirm_holder_stopped: true` and expected_lock_fingerprint from inspect. Do not supply/default the stopped confirmation on the caller's behalf.

- Plan validates request/namespace and records no intent, lock, transaction or file. It is not a stop confirmation generated by the product.
- Apply revalidates task identity, nested namespace, epoch and the exact expected task-lock content immediately before invoking existing breakLock. A changed lock refuses; never target a replacement holder based on an old inspection. Use bounded stable file-content hashing for the fingerprint, excluding volatile PID-liveness fields. Include explicit limits for any unobservable/oversized lock snapshot.
- Keep the existing archived old lock, previous holder, transaction evidence and break-record; do not delete unknown evidence, reclaim by age, overwrite a prior archive or convert partial recovery into success. Preserve generic error diagnostics and report uncertain effects if a filesystem failure occurs after a mutation may already have happened.
- The confirmation is an operator assertion recorded by core, not authenticated native stop proof. No process is killed or adopted. Remote/unobserved liveness remains unknown. This operation recovers only the task write lock, not the resource-domain lock or a running execution.

## Common behavior and scope

Default mutations are plan-only and write nothing; `--apply` is explicit. Success/read/plan exits 0, conflict/refusal/uncertainty 1, invalid request/options 2. Preserve nested task-lock/ledger/transaction/archive guards and system aliases above the domain. Do not introduce a second recovery journal, scheduler, lock service or task authority store. JSON/human output must distinguish recorded resolution, actual applied state transition, archived lock and unknown outcome.

Implementation is narrow app/CLI/schema glue, collaboration tests and both shipped guidance mirrors. Core semantics should remain unchanged; do not copy the legacy CLI's resolve-then-commit-on-transition-failure behavior. Portable bindings/native execution recovery remain subsequent slices.

## Verification and delivery

Use only fresh fixture domains: never reconcile, break a lock, release or mutate this live task for a test. Cover inspect/plan no effects; explicit resolution; illegal transition atomic refusal; missing attempt; stale epoch/revision; already resolved/missing uncertainty; approval/cancel/claims boundaries; explicit stop-confirmation required; changed lock fingerprint and new-holder refusal; archive evidence retention; nested symlink/FIFO/oversize refusal; separate-process contention and strict installed CLI from unrelated cwd. No real native/model launches.

Run meaningful focused and prior collaboration regressions, type checking/build, source policy/changed-file formatting/mirrors/package checks. Same Pi session/source claims; preflight this new pinned assignment before the first source write using a fresh actual observation, reusing it when valid. Return current manifest/input revision/prewrite evidence and one proactive product REPORT/notification; no polling, timer, completion wait, native fallback, extra agent, commit or publication.
