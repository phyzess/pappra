## Corrections before implementation

- `CollabNotifyReport.consumed: false` and `taskAccepted: false` explicitly state what a transport operation does not prove. They are not persisted recipient consumption flags that need to be flipped. Delivery records are mutable under their delivery lock: attempts/status are updated. Do not describe them as write-once.
- `src/collab/messages.ts` already persists correlated ACK and REPORT effects in authoritative task state. An ACK transitions an assigned attempt to accepted. Reuse these facts; an additional receipt must name a narrower, proven workflow action and must not become competing authority.
- A marker cannot make an external effect plus local record atomic. Persist an intent/reservation before dispatch; if a crash or network failure leaves the external outcome ambiguous, retain an actionable unknown state and reconcile supported observations. Neither marking before the effect nor marking afterward proves exactly-once execution. Never auto-repeat an ambiguous prompt, model continuation, launch or transfer.
- `deferred` is not permanently processed. A received ANSWER and an accepted ASSIGN can still require later work. Distinguish observed message, pending action, blocked action, issued action and verified completion; identify the existing durable primitive for each before adding schema fields. Cancellation and approval remain gates.
- `listMessagesForTaskRoot` is a bounded newest-first listing. A recovery scanner cannot ignore `truncated` or claim a complete inbox from the latest page. Define bounds and an honest incomplete result or stable cursor that cannot skip older unresolved messages. Old ready/blocked evidence must not suppress a newer corrective ANSWER.
- Native Pi observations are memory-only and not a network-reconnect detector, inbox or authorization mechanism. Supported session-start/settled callbacks can trigger a bounded reconciliation, but recovery must not depend on a callback firing after every outage. Do not mutate accepted observation-only lifecycle hooks into model-starting hooks. An explicit opt-in recovery extension/controller needs its own supported API and authorization contract.
- Review itself is not exactly-once merely because a processed file exists. A completed REPORT should produce a stable pending-review action keyed by report/input/coordinator epoch. Persist reviewer dispatch and correlate its result before marking progression complete; a coordinator restart must not lose that pending action or rerun the writer.
