# E2-A direction: bounded role and dependency planning

Implement a small read-only work-plan API over existing authoritative task records, messages, results and resource claims. This is the first implementation slice of role-aware parallel collaboration, not a new scheduler or an automatic launcher.

Exact permitted files: new `src/collab/work-plan.ts`, export in `src/collab/index.ts`, new `tests/collab/work-plan.test.ts`. Existing helpers may be read/reused but not edited without a concrete scope report. Keep legacy task/message/assignment schemas and behavior intact. Public access is through the existing `@phyzess/pappra/collab` export; CLI/MCP and the live multi-writer walkthrough follow after independent API review.

Define and document the minimal bounded plan format in this module: task/plan identity and owner epoch, unique node IDs, explicit assignment/attempt/input revisions, assignee and role labels, dependency edges and intended resource scope. Validate malformed/duplicate/unknown dependency references, self-dependencies and cycles before evaluation. Bound nodes/edges/strings and return actionable structured diagnostics. Role labels select responsibilities; they do not confer authority or require one specific harness. Support ordinary small single-writer plans without mandatory planner/reviewer/integrator nodes.

Evaluate a plan against supplied current authoritative snapshots without mutating records, claiming, dispatching, refreshing evidence, polling or calling models. Distinguish ready work, running work, awaiting independent review, rejected/failed dependencies and blocked/stale evidence. A completed or registered REPORT alone cannot unlock dependent work: require explicit current coordinator acceptance correlated to the exact predecessor node/attempt/input/report. Use stored registered message identity/content digest and the current owner epoch when validating an acceptance witness; do not trust an arbitrary `accepted:true` flag. Define the small optional ANSWER-body acceptance structure explicitly if existing messages have no suitable semantics; do not change core ANSWER processing or create another authority journal. Missing/old/mismatched/rejected acceptance remains blocked with a recovery action.

Existing same-domain claims/conflict helpers remain the resource authority. Planning may conservatively flag prospective overlap and show independently ready disjoint nodes, but cannot claim cross-domain fencing, OS enforcement or preflight/launch authority. Validate current assignment/assignee/attempt/input correlation and owner epoch rather than reusing stale plan readiness. A read-only result is advisory and must be re-evaluated before later explicit claim/dispatch. A writer cannot be its own sole review-acceptance authority; do not require the integrator to be a different person from the coordinator.

Tests must exercise a useful fork/join plan with independent workers and coordinator review, cycle/unknown-node refusal, failed/rejected predecessor, a successful REPORT awaiting acceptance, exact versus stale/mismatched acceptance, duplicate results without extra advancement, overlapping versus disjoint resource scopes and stale owner/input/attempt. Use existing deterministic task/message fixtures and primitives where useful; no fake live-host support claim.

Parallel writer: `pappra-investigator` in w3:p4 owns only the E3-A files under continuity; those expected edits may occur while you work. Do not compare a moving global manifest as if every parallel edit is unauthorized. Verify your exact baseline before edits; record your changed-file hashes and observed parallel changes separately. Only your three exact files are writable for this assignment despite older broad claims. Coordinator docs and E3 files are read-only.

Use a fresh isolated temporary compiler/test output directory and package-scope metadata as needed; do not clean/write shared `dist` or `.build`, modify package files, format another writer's files or run the full suite/package. Targeted tests, type checking and formatting of owned files suffice before the integration barrier. Report isolated-output setup and actual commands/results. Coordinator will build/retest the combined tree after both reports. Check matching pinned assignment/input/scope/runtime and new-assignment preflight before the first edit. Preserve selected model/settings and proactive product messaging; return one REPORT, no completion polling/timer/--wait/fallback/hidden workers.
