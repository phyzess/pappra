# Integrated delivery and independent acceptance

This checklist prepares the next complete integration batch while recovery final delivery and parallel work execution run. It does not initiate the full verification campaign or grant acceptance.

## Feature integration barrier

- Recovery public apply has mandatory exact session/cwd/harness/pane/current task binding and final authority checks; omitted or nullable inputs cannot disable them. Native callbacks use installed API shapes. Known no-effect retry, unknown non-replay and durable cause dedup remain intact.
- Parallel execution really overlaps disjoint ready workers; resource conflicts and integration paths serialize. Planner/writer/reviewer/integrator roles select responsibilities. Only actual independent coordinator acceptance unlocks dependent nodes; result pointers and repair paths remain durable.
- One integrator owns shared CLI registration/help and final public export/host bundle/skill/example updates. Read the current package scripts before using them: `prepare`, `prepack`, `pretest` and `package:check` can rebuild/clean shared outputs. Use an isolated copied source/dependency/build root, not the mutable checkout's dist/.build or a development temporary CLI as the delivered control plane.
- Accepted transition controller remains explicitly limited by absent native Pi interactive quiescence proof. A task-local retirement marker is not native archive or external route removal. Do not package a support claim contradicted by the adapter. Automatic handoff remains an unfinished objective, separate from deliverable supported recovery.

## One consolidated campaign after integration

Freeze and record one attributable source snapshot. Run source policy, production/test/script TypeScript checks, formatting, and full W/C/E regression from isolated outputs. Build/package that snapshot, verify archive contents and actual exported consumer APIs/CLI help/host entrypoints, install only into an isolated configuration and smoke-test the installed artifact. No registry publication or global settings changes.

Use this repository read-only as a selected real project with separate temporary workspace/knowledge/configuration roots for init, existing/new knowledge, reconfigure, runtime feedback, task/checkpoint and repository navigation. Preserve the user's accumulated dirty worktree. Do not treat checkout-only imports or private helper success as installed-consumer verification.

Use owned visible fixtures for the supported collaboration behaviors: two disjoint workers and independent review/aggregation; exact session/provider/model; interruption/restart with pending versus completed-result recovery; duplicates, stale messages and changed epochs; approval/cancellation/revoked claims; no unsafe requeue after unknown effects. Reuse accepted native tool-gate evidence unless integration changes that path. Unsupported real native takeover/automatic archive must stay reported unsupported, not replaced by a test-only receipt.

Group attributable failures, repair in the owning scope and rerun relevant checks. Repeat the final gate only when changed inputs require it. Coordinator independently accepts concrete behavior and evidence; worker completion, process exit, prompt submission and package creation are not acceptance.

## New-task session handoff

Use a new visible Pi session with Pi-configured OpenRouter for the integration assignment, not either implementation worker's grown context. Include only current objectives/scopes, accepted source/interface pins, unresolved findings and this checklist. Verify actual model/provider before source actions. Preserve old pending results; no archive/termination inference from this planning document. All implementation remains message-driven with isolated outputs and no model-completion polling.
