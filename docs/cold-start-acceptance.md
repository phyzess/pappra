# Cold-start acceptance (bounded observations)

Four fresh-agent cases and a subsequent protocol repair were observed during
beta.20 development. Initial goals described the product task and operational
constraints; they did not prescribe Pappra roles or an implementation recipe.
Saved native call/result prefixes and private byte-pinned receipts support these
observations. They are not a guarantee about future role selection.

## Read-only Pi investigation

A fresh Pi reached the project skill and selected-repository code entry, found
the missing runtime archival exit, and passed 55 focused checks. No source was
changed. This establishes the observed discovery route, not writer behaviour.

## Codex archival implementation: negative role-selection control

A fresh Codex implemented the archival exit and passed 65 affected checks,
including 13 process-kill recovery cases. It did not arrange independent review.
This failure is retained. The project guidance was then made explicit: changes
to authority, ownership, persistence, recovery or release execution require an
independent native reviewer. Later review does not rewrite this initial outcome.

## Pi passive diagnostics

A fresh Pi implemented passive doctor diagnostics and nine new tests; related
51-test and 33-test groups passed. It judged direct work appropriate for passive
diagnostics. An unnecessary full suite was started and aborted; it is not a pass.
The coordinator subsequently requested independent archive/doctor review before
publication. This case does not establish automatic delegation.

## Codex checkpoint persistence: independent review selected

A fresh Codex chose and started a native reviewer before editing. The pair used
Pappra assignments, observed capability evidence, ACK, REPORT and explicit
coordinator acceptance. Fifty-seven focused checks passed. Independent review
caught an ownership-capture scheduling window; the implementation was corrected.
Daily host configuration was preserved, without built-in Codex subagents.

Node cannot atomically delete a directory conditional on its filesystem identity;
the bounded cleanup checks are not an operating-system security fence.

## Release failure and real-record recovery

The initial checkpoint review released its claims but failed to register STATUS:
a null correlation was invalid for the envelope's reply_to contract. That failure
and its original evidence were preserved.

A separate Pappra writer/reviewer task corrected pre-effect validation and derived
the genuine ASSIGN correlation. The writer passed 82 affected checks, including
15 focused regressions; the independent reviewer exercised those 15 against the
rebuilt CLI. Both nodes were explicitly accepted and released their claims.

The original native reviewer then used the original request on the original task.
First recovery and one identical replay both exited 0. A genuine correlated
STATUS was registered; original intent, acceptance, results and identity data
were preserved, and replay added no effects. Active claims were zero.

Native notification could not verify the sandboxed caller pane. That delivery
warning remains visible: persisted recovery is proven, successful notification is
not. No native execution or stopped process was inferred from a protocol record.

## Limits

Cold-start acceptance is closed for these bounded cases, including the retained
negative control. It does not establish universal autonomous scheduling, fully
unattended approvals, provider recovery, all-host compatibility or publication.
Integration checks and installed-package verification are separate release gates.
An existing MCP process may still run older code after rebuilding or reinstalling;
inspect its selected executable and reload the host explicitly when required.
